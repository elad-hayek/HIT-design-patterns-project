# common_rejects_design_patterns : Sheet1

This following lists common rejects in projects that students submit in the Design Patterns course. These are the common rejects only. This is not a complete list of the possible rejects.

| Reject Code | Explanation |
| :--- | :--- |
| COMMENTS | missing C/C++ comments (comments that start with `//` and comments that start with `/*` and ends with `*/` => make sure that you have comment (type C++) every 8-10 lines. |
| API | missing JavaDoc API comments (`/** */`). every class/interface/enum/function/variable should have api comments |
| PDFNAME | the name of the pdf file is not the name of the team manager (in English) |
| ZIPNAME | the name of the zip file is not the name of the team manager (in English) |
| TWOFILES / FOURFILES / THREEFILES | when the requirement is to submit two/four/three files and something else was submitted |
| FUNCTIONNAME | small letters only (except for cases in which the name includes more than one word... in those cases we expect having camel case) |
| VARIABLENAME | small letters only (except for cases in which the name includes more than one word... in those cases we expect having camel case) |
| CLASSNAME | The name of every class should start with a capital letter |
| OBJECTNAME | The name of every object should start with a capital letter |
| TRAITNAME | The name of trait object should start with a capital letter |
| FILENAME | when the name of the file is not according to the guidelines |
| VIDEO | missing video or video is not available as unlisted on youtube |
| CLICKABLE | the pdf file should include a clickable link to the video |
| BROKENLINES | when there are broken lines in the PDF document => make sure all lines are not broken.. you can use a font with a smaller size... you can change the pdf document to be landscape instead of portrait |
| CODEFORMAT | when the format of your code in the PDF document is lousy (e.g. when the code is aligned to the right/center) => go over the PDF and make sure it looks clear in order to allow the code review |
| VAL | you should use val when possible. if val doesn't fit you should use var instead. |
| PRIVATE | all members of a class/object/trait must be private unless there is reason for not using private |
